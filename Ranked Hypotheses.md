Ranked Hypotheses
1. SendLevel prevents the programmatic Send from triggering the ~#!+0 hotkey
Mechanism: By design, AutoHotkey prevents Send commands from triggering its own hotkeys to avoid infinite loops. A standard Send("#!+0") executes at SendLevel 0. Because the ~#!+0:: hotkey operates at the default InputLevel 0, it will completely ignore the programmatic keystrokes.
Split-brain side effect: The synthetic keystroke might still reach the OS (and potentially handy.exe), but the ~#!+0:: AHK handler is never invoked. Therefore, g_DictationActive is never set, and the red indicator never appears.
How to falsify: Add a debug log at the very top of ~#!+0::. Press ^!#4. If the log does not appear, this hypothesis is confirmed.
Code Path: The Send("#!+0") call inside ^!#4:: vs the ~#!+0:: hotkey definition.
2. handy.exe ignores synthetic (injected) keystrokes
Mechanism: Many background dictation applications register low-level keyboard hooks (using SetWindowsHookEx) and intentionally ignore keystrokes flagged with LLKHF_INJECTED. Even if we bypass the SendLevel issue to trigger the AHK logic, handy.exe itself may simply refuse to start recording because the #!+0 was generated by software rather than physical hardware.
How to falsify: (Assuming H1 is fixed or bypassed) check if the AHK red indicator appears, but the handy.exe "Recording" window never spawns.
Code Path: The interaction between AHK's Send API and handy.exe's global hook.
3. Stale g_DictationActive state preventing the Send
Mechanism: The programmatic trigger is wrapped in if (!g_DictationActive). If a previous dictation session ended abnormally (e.g., the handy.exe window was closed externally or a timer failed to clean up), g_DictationActive might be permanently stuck as true.
How to falsify: Log the value of g_DictationActive immediately inside the ^!#4:: hotkey, before the if statement. If it outputs 1 (true) while dictation is physically off, this is the culprit.
Code Path: The if (!g_DictationActive) gate in ^!#4:: and the state cleanup logic in CheckDictationRecordingWindow().
4. Cross-Process Mutex Ownership (g_DictationHotkeyIsOwner is false)
Mechanism: The codebase uses InitializeDictationHotkeyOwnership() to create a named mutex (Local\D2C_Dictation_Hotkey_Owner). If there is a zombie Utils.ahk or AutoHotkey64.exe process running in the background, that phantom process holds the mutex. Your active script evaluates g_DictationHotkeyIsOwner as false and exits the ~#!+0:: hotkey immediately.
How to falsify: Check Task Manager for duplicate AutoHotkey*.exe processes. Alternatively, log the value of g_DictationHotkeyIsOwner at the top of the hotkey.
Code Path: ~#!+0:: early exit: if (!g_DictationHotkeyIsOwner) return.
5. KeyWait / Physical Modifier Masking Conflict
Mechanism: When you press ^!#4, you are physically holding down Ctrl, Alt, Win, and 4. For AHK to send #!+0 (Win+Alt+Shift+0), it must synthetically release Ctrl, inject Shift and 0, and restore Ctrl. Because ~#!+0:: contains KeyWait("0", "L"), the rapid injection of the 0 key state while physical modifiers are held down can cause the logical state to misalign, either causing KeyWait to hang or the hotkey to exit prematurely.
How to falsify: Change Send("#!+0") to SendEvent("#!+0") or add KeyWait("Ctrl") / KeyWait("Alt") before the Send call to ensure physical keys are released before synthetic ones are pushed.
Code Path: Send("#!+0") in ^!#4:: intersecting with KeyWait("0", "L") in ~#!+0::.
