Hypothesis 1: The Overlay is Not the "Active" (Foreground) Window (Most Likely)

Mechanism: The WinActive() function strictly checks if the target window currently holds the OS input focus. If Handy's "Recording" or "Recording Overlay" windows are floating tool-windows (which intentionally do not steal focus from the user's primary app like Chrome or Word), WinActive() will evaluate to false. The script then falls through to SendInput "{Escape}", which Handy receives, thus closing the dictation.
How to falsify/test: Change WinActive to WinExist in the if condition. If WinExist("Recording ahk_exe handy.exe") correctly blocks the Escape key, it confirms the window was present but simply not focused.
2. Hypothesis 2: Window Title or Class Mismatch

Mechanism: The window titles might not be exactly "Recording" or "Recording Overlay". Tauri applications sometimes use invisible host windows, append hidden spaces to titles, or use dynamic titles (e.g., "Recording...").
How to falsify/test: Inject a debug log inside the Escape:: hotkey that logs the title of the currently active window and all existing handy.exe windows to debug.log.
Action: Have the Junior AI write a loop using WinGetList("ahk_exe handy.exe"), retrieve their titles using WinGetTitle, and dump them to a file whenever Escape is pressed.
3. Hypothesis 3: Synthetic Keystroke Leakage (SendInput is caught by Handy)

Mechanism: If the if condition fails for any reason, the hotkey executes SendInput "{Escape}" to pass the key down to the system. Handy may be using a low-level global hook (SetWindowsHookEx) that listens for all Escape presses, including synthetic ones generated by AHK.
How to falsify/test: Add a log line right before SendInput "{Escape}" (e.g., FileAppend("Escape fell through and was sent synthetically.\n", ...)). If you press Escape, see this log, and Handy closes, it means the condition failed. If you don't see this log, but Handy still closes, Handy is bypassing AHK's hook entirely.
4. Hypothesis 4: Hook Precedence (Handy catches physical key before AHK)

Mechanism: AutoHotkey uses #UseHook and #InputLevel 10 which is generally very strong. However, if Handy initializes its global keyboard hook after AHK launches, Windows might pass the physical Escape keypress to Handy first.
How to falsify/test: Reload Utils.ahk while Handy is already open and recording. If reloading the script fixes the issue for that session, it is a hook-order precedence issue.
5. Hypothesis 5: Cross-Process Sentinel Interference

Mechanism: Looking at the Escape:: hotkey in Utils.ahk, there is a block of code right before the Handy check that looks for .cursor\wm_selector_open. If this file erroneously exists (e.g., a previous crash left the sentinel file behind), the script writes to wm_selector_close_request and returns immediately, consuming the Escape. Wait, if it consumes the Escape, Handy wouldn't close. If Handy is closing, it means this block isn't catching it. (This makes it less likely to be the culprit for Handy closing, but good to keep in mind if Escape stops working entirely).
