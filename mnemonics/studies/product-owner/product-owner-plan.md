## Phase 0: Cognitive Translation Layer (Pre-work)

### From Usability to Business Value

#### Customer Value and Knowledge Value

- [ ] Watch Kniberg's value curve and internalize Customer Value vs Knowledge Value
- [ ] Prioritize Knowledge Value items (spikes, prototypes, experiments) when uncertainty is high
- [ ] Shift focus to Customer Value as uncertainty drops and the value curve steepens
- [ ] Recognize when to stop delivering low-value "bonus features" and reallocate the team

**🔗 Resources:**

- [Henrik Kniberg: Agile Product Ownership in a Nutshell](https://www.youtube.com/watch?v=502ILHjX9EE)

#### Scope, Speed, and Constraint Negotiation

- [ ] Internalize "trimming the tail" — cut scope when the value curve flattens
- [ ] Balance building the right thing, building it right, and building it fast as PO arbiter
- [ ] Default to speed to accelerate feedback loops and empirical learning
- [ ] Negotiate scope reduction (not timeline extension) under fixed-time constraints
- [ ] Reframe primary objective from user delight to ROI and business viability
- [ ] Reframe value definition from frictionless journeys to Customer + Knowledge Value composite
- [ ] Replace feature-completeness scope pushes with thin functional slices
- [ ] Replace "more time to perfect" requests with ruthless scope cuts on fixed deadlines

## Phase 1: Agile Foundations and Backlog Architecture (Months 1–2)

### Topic Module 1.1: Empiricism and the Product Owner Paradigm

#### Empiricism and Mindset

- [ ] Internalize empiricism: decisions from observed real-world data, not assumptions
- [ ] Distinguish project mindset (output, budgets, schedules) from product mindset (outcomes, learning)
- [ ] Act as singular voice of value bridging business strategy and tactical execution
- [ ] Complete Scrum.org PSPO learning path through Professional Scrum Product Owner I readiness
- [ ] Validate assumptions in the market as early as possible

**🔗 Resources:**

- [Scrum Guide](https://scrumguides.org/scrum-guide.html)
- [Scrum.org: Product Owner Learning Path](https://www.scrum.org/pathway/product-owner-learning-path)

### Topic Module 1.2: The Architecture of User Stories

#### Stories as Conversation Placeholders

- [ ] Treat User Stories as placeholders for conversation, not exhaustive requirement documents
- [ ] Avoid over-prescriptive upfront detail that removes engineering creativity
- [ ] Avoid under-specification that causes rework (grocery delivery analogy)
- [ ] Master timing of detail insertion — define specifics just before work starts
- [ ] Use Conditions of Satisfaction (not Acceptance Criteria) to retain PO ownership of value
- [ ] Write "strong password" stories with detail deferred until refinement

**🔗 Resources:**

- [Mike Cohn: User Stories Applied (book)](https://www.mountaingoatsoftware.com/books/user-stories-applied)
- [Mountain Goat Software: User Stories vs Requirements](https://www.youtube.com/results?search_query=Mountain+Goat+Software+User+Stories+vs+Requirements)
- [Mountain Goat Software: Writing User Stories](https://www.youtube.com/results?search_query=Mountain+Goat+Software+Writing+User+Stories)

### Topic Module 1.3: Story Splitting and Release Mapping

#### Vertical Slicing and SPIDR

- [ ] Unlearn slicing by design layers or user flows only
- [ ] Avoid splitting along technical boundaries (database vs front-end)
- [ ] Master vertical slicing: thin, end-to-end, independently deployable slices
- [ ] Apply SPIDR framework (Spikes, Paths, Interfaces, Data, Rules) to split epics
- [ ] Build a User Story Map to visualize journey, organize backlog, and plan releases

**🔗 Resources:**

- [Mountain Goat Software: SPIDR Story Splitting](https://www.youtube.com/results?search_query=Mountain+Goat+Software+SPIDR+story+splitting)

#### Phase 1 Milestone: Backlog Architecture Document

- [ ] Deconstruct one high-level Epic into 10+ independent User Stories using SPIDR
- [ ] Ensure no story is split along technical boundaries
- [ ] Write minimum viable Conditions of Satisfaction for each story without over-prescribing solutions
- [ ] Present Backlog Architecture Document in a sprint review for feedback

## Phase 2: Continuous Discovery and Strategic Alignment (Months 3–4)

### Topic Module 2.1: Institutionalizing Continuous Discovery Habits

#### Product Trio and Weekly Touchpoints

- [ ] Treat discovery as a continuous daily habit, not a phased upfront activity
- [ ] Operate within a Product Trio (PO, Lead Designer, Lead Engineer)
- [ ] Conduct weekly customer touchpoints as shared trio responsibility
- [ ] Resist skipping discovery even under AI-accelerated delivery pressure
- [ ] Accept that slowing on discovery is the fastest path to shipping the right thing

**🔗 Resources:**

- [Teresa Torres: Continuous Discovery Habits (book)](https://www.producttalk.org/continuous-discovery-habits-book/)
- [Product Talk: Continuous Discovery Habits](https://www.youtube.com/results?search_query=Teresa+Torres+Continuous+Discovery+Habits+Product+Talk)

### Topic Module 2.2: The Opportunity Solution Tree (OST)

#### Four-Tier OST Framework

- [ ] Define a singular measurable Desired Outcome rooted in OKRs (not revenue-only)
- [ ] Frame Opportunity Space from customer perspective ("I struggle to…"), not feature requests
- [ ] Never let customers design solutions — PO owns solution space
- [ ] Generate at least three distinct solutions per prioritized opportunity
- [ ] Design fast assumption tests for value, usability, viability, and feasibility before production code
- [ ] Retrofit every backlog feature to a validated opportunity and strategic outcome

**🔗 Resources:**

- [Teresa Torres: Opportunity Solution Trees](https://www.producttalk.org/opportunity-solution-trees/)
- [Product Talk: Opportunity Solution Tree Tutorial](https://www.youtube.com/results?search_query=Teresa+Torres+Opportunity+Solution+Tree)

#### Phase 2 Milestone: Opportunity Solution Tree

- [ ] Map one Desired Outcome through at least 4 Customer Opportunities
- [ ] Brainstorm 12 distinct Solutions (3 per opportunity minimum)
- [ ] Design 4 assumption experiments linked to specific solutions
- [ ] Present completed OST in sprint review for critical feedback

### Topic Module 2.3: Escaping the Build Trap and Lean Strategy

#### Hypothesis-Driven Product Definition

- [ ] Shift from requirements-driven to hypothesis-driven product definition
- [ ] Frame every roadmap item as a testable hypothesis (Lean Product Canvas)
- [ ] Measure success by customer behavior change driving business value, not feature delivery
- [ ] Translate qualitative UX work into quantitative business risk mitigation language
- [ ] Create Product Vision, Product Strategy, and outcome-based GO Product Roadmap (Pichler)
- [ ] Replace feature-timeline roadmaps with outcome charts discovery can fill in

## Phase 3: Prioritization Frameworks and Metric Architecture (Months 5–6)

### Topic Module 3.1: Quantitative Prioritization via the RICE Framework

#### RICE Scoring Mechanics

- [ ] Reject intuition-only prioritization in favor of structured scoring
- [ ] Score Reach: users/transactions affected in a defined timeframe
- [ ] Score Impact on standardized scale (3 Massive → 0.25 Minimal)
- [ ] Score Confidence as percentage penalty for speculative estimates
- [ ] Score Effort in person-months (under one month = 0.5 per Intercom convention)
- [ ] Calculate (Reach × Impact × Confidence) / Effort for each initiative
- [ ] Document qualitative reasoning behind Confidence and Effort to surface bias
- [ ] Recognize RICE pitfalls: input quality sensitivity and undervalued foundational work

**🔗 Resources:**

- [Intercom: RICE — Simple Prioritization for Product Managers](https://www.intercom.com/blog/rice-simple-prioritization-for-product-managers/)

#### Phase 3 Milestone: RICE Matrix Evaluation

- [ ] Score 15 diverse hypothetical backlog features with exact RICE calculations
- [ ] Document Confidence and Effort reasoning for each item
- [ ] Present prioritized matrix in sprint review and defend top vs bottom rankings

### Topic Module 3.2: Qualitative Prioritization via the Kano Model

#### Kano Feature Categories

- [ ] Classify features as Basic Expectations (must-haves; dissatisfaction if absent)
- [ ] Classify features as Performance Payoffs (satisfaction scales with quality)
- [ ] Classify features as Excitement Generators (unexpected delighters)
- [ ] Balance RICE quantitative rigor with Kano emotional mapping in backlog planning

**🔗 Resources:**

- [Kano Model Explained for Product Managers](https://www.youtube.com/results?search_query=Kano+Model+product+management+explained)

### Topic Module 3.3: Analytics and the North Star Metric

#### Metric Trees and NSM

- [ ] Distinguish lagging output metrics (revenue) from actionable leading indicators
- [ ] Construct Metric Trees bridging business goals to daily product work inputs
- [ ] Identify a true North Star Metric capturing core customer value delivered
- [ ] Run metric tree workshops across Marketing, Sales, and Engineering
- [ ] Align Scrum team bets to initiatives that drive systemic NSM impact

## Study Architecture: Learning Sprint Cadence (Ongoing)

### Bi-Weekly Learning Sprints

- [ ] Sprint Planning (bi-weekly): pull specific topic modules into active learning backlog
- [ ] Daily Standup: 15-minute journal on concepts mastered, blockers, and UX→PO synthesis
- [ ] Execution: maintain 50/50 theory (texts, videos) vs practice (artifacts, simulations)
- [ ] Sprint Review: present physical artifacts to peer, mentor, or Agile coach
- [ ] Sprint Retrospective: adjust study habits to optimize next sprint velocity
